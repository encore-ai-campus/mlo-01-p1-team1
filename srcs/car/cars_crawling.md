# 중고차 데이터 수집·적재 파이프라인

## 프로젝트 개요

중고차 API 서버의 목록 및 상세 페이지에서 차량 정보를 수집하고, 크롤링 서버에서 데이터를 정제한 뒤 MySQL 서버에 직접 적재하는 서버 기반 ETL 파이프라인입니다.

일반적인 파일 기반 수집 방식과 달리 원천 데이터를 JSON·CSV·TXT 등의 중간 파일로 저장하지 않습니다. 수집한 데이터는 크롤링 서버의 메모리에서 정제·검증한 후 MySQL에 바로 적재합니다.

이를 통해 파일 입출력과 중간 산출물 관리 비용을 줄이고, MySQL을 데이터의 단일 관리 지점으로 유지하여 파일 중복과 동기화 문제를 최소화했습니다.

최초 실행 시 최대 500페이지의 데이터를 전체 적재하고, 이후에는 Linux cron을 통해 15분마다 신규 차량만 선별하여 저장합니다.

> API Key TXT 파일은 원천 데이터가 아닌 인증정보를 관리하기 위한 캐시 파일입니다.

## 핵심 기능

### 1. 서버 기반 데이터 수집 및 직접 적재

중고차 API 서버에서 차량 목록과 상세 정보를 수집한 뒤 `pandas`를 이용해 숫자·날짜 형식으로 정제합니다.

정제된 데이터는 별도의 JSON·CSV 파일을 생성하지 않고 SQL DB 서버의 `car_data` 테이블에 직접 적재합니다.

**처리 흐름**

API 서버 → 차량 데이터 크롤링 → 데이터 정제 → 신규 데이터 선별 → MySQL 적재

### 2. 초기 전체 적재와 증분 적재

- 최초 실행 시 전체 페이지를 순회하여 DB에 없는 차량을 모두 저장합니다.
- 이후 `cron`을 통해 15분마다 크롤러를 실행합니다.
- `car_id`를 기준으로 DB에 이미 존재하는 차량을 제외하고 신규 차량만 저장합니다.
- 신규 데이터가 없는 구간에 도달하면 크롤링을 조기 종료하여 불필요한 요청을 줄입니다.

### 3. API Key 자동 관리

매일 갱신되는 API Key를 자동으로 조회하여 서버 내부 TXT 파일에 저장합니다.

15분마다 크롤러가 실행될 때 저장된 API Key를 읽어 사용하며, 요청 도중 `403 Forbidden`이 발생하면 새로운 Key를 발급받아 TXT 파일을 갱신하고 같은 URL을 다시 요청합니다.

이를 통해 API Key를 코드에 직접 작성하지 않고 정기 크롤링을 자동으로 운영할 수 있습니다.

### 4. 크롤링 요청 예외 처리

`requests.get()` 실행 결과를 확인하여 존재하지 않는 URL이나 HTTP 요청 실패를 처리합니다.

- 연결 실패와 시간 초과: 일정 시간 후 같은 URL 재시도
- `403`: API Key 갱신 후 재시도
- `429`: 서버가 전달한 대기시간 이후 재시도
- `5xx`: 서버 장애로 판단하여 일정 시간 후 재시도
- 존재하지 않는 URL 및 기타 HTTP 오류: 로그 기록 후 해당 요청 처리 중단

요청 오류 로그에는 발생 시각, 오류 레벨, 요청 URL과 오류 내용을 기록합니다.

**로그 경로**

`/home/ec2-user/logs/request/non-exists-url-error.log`

### 5. MySQL 적재 예외 처리

DB 적재 과정에서 발생하는 오류를 연결 오류와 SQL 오류로 분리하여 관리합니다.

- 네트워크 및 연결 오류는 연결 풀을 초기화한 뒤 최대 3회 재시도합니다.
- 중복 키와 데이터 형식 오류는 쿼리 오류 로그에 기록하고 실행을 중단합니다.
- 트랜잭션을 사용하여 저장 도중 문제가 발생하면 전체 작업을 자동으로 Rollback합니다.
- 저장에 성공한 경우에만 Commit하여 부분 적재를 방지합니다.

| 오류 구분 | 처리 방법 | 로그 경로 |
|---|---|---|
| DB 연결 및 네트워크 오류 | 연결 초기화 후 최대 3회 재시도 | `/home/ec2-user/logs/sql/sql-connection-error.log` |
| 중복 키 및 무결성 오류 | Rollback 후 로그 기록 및 중단 | `/home/ec2-user/logs/sql/sql-query-error.log` |
| 데이터 형식 오류 | Rollback 후 로그 기록 및 중단 | `/home/ec2-user/logs/sql/sql-query-error.log` |
| 기타 SQL 오류 | Rollback 후 로그 기록 및 중단 | `/home/ec2-user/logs/sql/sql-query-error.log` |

### 6. 적재 결과 및 상태 확인

크롤링과 DB 적재가 정상적으로 완료되면 수집 시각과 저장된 데이터 건수를 상태 로그에 기록합니다.

**로그 경로**

`/home/ec2-user/logs/health-check/healthy.log`

로그에는 다음 정보가 포함됩니다.

- 작업 완료 시각
- 수집 및 저장된 데이터 개수
- 로그 레벨

### 7. 구현 성과

- 초기 전체 적재와 정기 증분 적재를 하나의 실행 파일에서 옵션으로 분리했습니다.
- `car_id` 기준의 이중 중복 제거로 같은 실행 내부와 DB 기존 데이터의 중복 저장을 방지했습니다.
- 매일 변경되는 API Key를 자동으로 갱신해 무인 운영 가능성을 높였습니다.
- 숫자·날짜 데이터를 DB 컬럼 형식에 맞게 변환하고 잘못된 값은 즉시 감지하도록 구성했습니다.
- API 오류와 DB 오류를 분리해 장애 원인과 확인할 로그 파일을 명확하게 했습니다.
- 트랜잭션과 제한적 재시도를 적용해 부분 저장 및 일시적 연결 장애에 대응했습니다.
